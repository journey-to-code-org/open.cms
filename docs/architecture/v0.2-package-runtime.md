# Package-driven runtime (0.2.0)

## Active-site selection

`npm run dev -- --site ./sites/demo-region` and `npm run build -- --site ./sites/demo-region` select a package explicitly. The corresponding Garrett commands use `./sites/garrett-county`. If omitted, the development/build default is the fictional demo. Relative CLI paths resolve from the current working directory, including sibling/private package repositories; package manifest entries remain contained inside the selected package root.

`scripts/active-site.mjs` resolves the CLI input. `scripts/site-package-fs.mjs` loads the manifest and values, reuses the shared 0.1.x validators, checks filesystem containment and symlinks, validates package references, and normalizes place GeoJSON. It returns a `LoadedSite` object containing the package manifest, site config, navigation, pages, collections, normalized places, trail snapshot, Markdown records, map, theme, and resolved paths. Browser code uses `virtual:open-cms-site`, generated from this validated object.

The shared pure checks stay in `shared/site-validation.mjs`; Node-only filesystem work stays in `scripts/site-package-fs.mjs`. The page component registry and its presentation variants are allowlisted. Package content and navigation links are escaped or checked before rendering. Theme values use constrained color/font formats; optional package CSS is loaded from a path-contained manifest entry, with `@import`, `url(...)`, and `expression(...)` rejected. Asset trees reject symlinks and special files. Page and content image paths use root-style public URLs and resolve only to existing files inside the selected package's `assets/` directory. Explorer-facing editorial copy is optional package configuration with neutral engine defaults.

The declarative home-page presentation surface currently allows `hero` variants `default` and `landscape`, and `guide-collection` variants `default` and `image-cards`. Hero images and Markdown frontmatter `image` fields use the same validated package asset convention. These choices select engine-owned markup and styles; packages do not provide templates or JavaScript.

## Static generation

`scripts/content-site.js` consumes a `LoadedSite`. It renders home composition from the validated page sections, article pages from Markdown content, navigation, canonical URLs and descriptions, sitemap/robots output, and install identity. Markdown HTML is sanitized through a small tag/attribute allowlist. Vite serves the same generated content during development and emits it to `dist/` for ordinary static hosting.

The build writes the PWA manifest from `config.pwa`, uses the selected package's asset directory as Vite's public directory, combines engine CSS with validated theme tokens and package theme CSS, and versions service-worker caches by site ID and output hash. Vite serves the same `buildSiteStylesheet()` output at `/site.css` during development and writes it to `dist/site.css` in production. The explorer receives the same tokens and package theme CSS through its validated runtime module. Public Mapbox credentials remain separate from the package and accept only the `pk.` public-token form.

## Geographic runtime

Places are normalized once at load time. The map and discovery tools consume `runtime.places` and `config.region.bounds`. Bounds feed map limits and zoom, Overpass BBOX construction, snapshot clipping, and GPX regional provenance. Package trail snapshots retain OpenStreetMap source IDs, attribution, retrieval dates, route/path distinction, and regional-only semantics. Browser refreshes remain abortable and bounded; cached results cannot erase bundled records.

`src/region.ts` has no regional constants. Its clipping, containment, BBOX, and minimum-zoom functions accept bounds. Rust adds bounds validation, point containment, and Liang-Barsky segment clipping. On startup, the app serializes all bundled hike geometries as one grouped operation and consumes the Rust-clipped result. If WASM cannot initialize, it logs the issue and uses the TypeScript-validated clipped snapshot. The existing GPX worker remains unchanged in responsibility.

## Web Component boundaries

| Element | Runtime data | Event/interface |
| --- | --- | --- |
| `<open-cms-place-list>` | normalized places, selected place ID | `place-select` with `{ place }` |
| `<open-cms-hike-list>` | filtered regional hikes and region name | `hike-preview`, `hike-analyze`, `hike-export`, each with `{ hike }` |
| `<open-cms-notice>` | message and error state | `show(message, error?)` |

`app.ts` still coordinates Mapbox lifecycle, query/filter state, offline storage, refresh/cancel flows, analysis worker requests, and selection between map and panels. The elements own list rendering and status announcements; this is an incremental extraction, not a complete UI rewrite.

## Legacy boundary and limits

The explorer no longer imports root `src/model/geo.json` or `src/model/hikes.json`; those legacy files and the disconnected Garrett UI tree were removed. The old root article-only generator and its fixed public asset list were removed. `content/` remains as historical source material for the migration; live content is loaded from the selected package. `docs/README.md` remains the Garrett deployment/data guide. Historical Garrett references inside `sites/garrett-county/` and tests of that fixture are expected.

Static HTML remains the output. A Mapbox token and live Overpass service are optional network dependencies for map tiles and refreshes. The current Markdown renderer supports headings, paragraphs, lists, links, emphasis, and safe authored HTML; it is intentionally not a general-purpose CMS editor. The content pages use a shared engine template, so site-specific art direction and richer block types can grow through the package format later.
